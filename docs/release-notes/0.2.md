# What's in 0.2

Effect Schema HTTP 0.2 delivers the workflow the library is built around: define a request once,
adjust it where it is used, and run it. It also removes the places where the library refused or
rewrote a request on its own, so what a request declares is what your HTTP client receives.

`0.2.0` is a breaking release, and it is being prepared: it is not published yet, so an ordinary
install still gives you `0.1.0`. The [version policy](../versions.md) explains installation and
updates, and the [detailed changelog](../changelog.md) records individual changes. Read the next
section before you update.

## Check your paths first

One change compiles and still changes your URLs, so start here. `Request.path` used to replace
whatever came before it. It now adds to it: a path is the constructor's path followed by what each
`Request.path` adds, in order, with no `/` added or removed.

This definition compiles on both versions:

```ts [0.1]
const getUser = Request.get("/users").pipe(
  Request.path(Schema.FiniteFromString, (id, encode) => `/users/${encode(id)}`),
);
```

On `0.1` it asks for `/users/42`. On `0.2` it asks for `/users/users/42`, and nothing warns you.

### What a wrong URL can do

The compiler does not help here, and a wrong URL does not always fail. As a rehearsal, this project
migrated its own integration tests, which agents wrote. Moving 21 `Request.path` calls gave no
compile errors from the path change, and 77 of 1010 tests then failed at run time:

| What happened                                                 | Tests |
| ------------------------------------------------------------- | ----- |
| The client refused the URL as invalid                         | 6     |
| The answer matched no declared case: `UnexpectedResponse`     | 27    |
| The answer did not decode: `DecodeError`                      | 7     |
| Another check in the test failed                              | 16    |
| A declared case came back as an ordinary value, with no error | 21    |

These counts come from agent-written code, so they do not predict what your application will see.
They show what a wrong URL can do, and the last row is the reason to read this section. A declared
404 came back as a `NotFound` value for a resource that exists. A rollback's DELETE got a 404 and
left its rows in place, with no error. One wrong URL landed on a different declared case. An
application with no test that checks the URL gets no signal at all.

### Find them by reading

Read your definitions, because nothing else finds these. The compiler accepts them, and only a test
that reaches the URL and checks it can fail.

Treat any constructor with path text as suspect, even a placeholder. Go through every `Request.path`
and follow it to its constructor, which can be in another file. Look for:

- **A path the renderer repeats,** as in the example above.
- **A label,** such as `Request.get("/users/:id")` or `Request.get("{location}")`. It never reached
  the URL on `0.1`, and now it does.
- **A constructor that exists to carry a query or fragment,** such as
  `Request.get("/elsewhere?lang=de#closing")`. The path in front of them looks real, and it never
  reached the URL either.
- **More than one `Request.path` on a request,** including one added to an imported request.

A constructor that carries a query or fragment keeps only those:

<<< ../../examples/migration-0-2.ts#path-carrier

A label fails differently on each platform, so a run on one proves nothing about another. With no
base URL, `{location}` fails in Node as an invalid URL. In a browser it can succeed with no error,
because a relative URL goes to the page's own server. With a base URL it reaches your service as
`/%7Blocation%7D/...`, wherever it runs.

### If you move to a template

A renderer keeps working, so moving to the new [path template](../modules/request.md#path-and-body)
is your choice. It changes the input's shape:

<<< ../../examples/migration-0-2.ts#path-template

Let the compiler lead this change, because a text search misses a call such as
`(path) => remove.execute({ path })`. The compiler finds that, and a stale `Request.mapInput` too.

- **Errors can come in two rounds.** A hand-written input type hides its callers. The first error is
  at the `execute` that takes it, and the callers only appear once you correct that type.
- **A scalar renderer cannot stack with a template.** That makes the input impossible to supply,
  which shows at `execute`. Move both, or give the renderer a struct.
- **A stale scalar that gets past the types fails loudly.** `path: 42` through a cast or from
  JavaScript fails with `SchemaError: Expected object`, before anything is sent.

A helper that takes a suffix at run time cannot become a template, because a template's text is
fixed when it is written.

Before:

```ts [0.1]
const customerPath = (suffix: string) =>
  Request.path(
    Schema.String,
    (customer, encode) => `/customers/${encode(customer)}${suffix}`,
  );

const getArchive = Request.get("").pipe(customerPath("/archive"));
```

After, each use writes its own template:

<<< ../../examples/migration-0-2.ts#path-suffix

Or keep the helper as it is, because a renderer after `Request.get("")` is unchanged.

## Define once, adjust where it is used

A definition now describes the most common request, not the only one. `Operation.make` keeps its
parts, so a component can derive a variant without copying anything:

<<< ../../examples/recipes/adjust-a-definition.ts#adjust

`getThings` does not change, and the variant's type holds only what it can return. Requests,
responses and options can each be adjusted, and a [mapped
operation](../modules/operation.md#adjust-a-mapped-operation) stays adjustable. [`Response.replace`
and `Response.remove`](../modules/response.md#adjust-a-contract) change one case and keep the rest,
and [Recipes](../recipes.md) shows this in a complete component. Generators work wherever an
operation runs, and the guides now show both styles.

## Paths read like paths

`Request.path` also works as a tagged template, with values declared by `Request.pathValue`. A child
endpoint adds to its parent with no schema spread or hand-written renderer, and its input is
inferred:

```ts
import { Request } from "viell-effect-schema-http";

const customer = Request.pathValue("customer");
const calendar = Request.pathValue("calendar");

const getCalendar = Request.get("").pipe(
  Request.path`/customers/${customer}/calendars/${calendar}`,
);
```

Each value goes through its own schema and the path encoder, and a plain string in a template is a
compile error. [Nested resource paths](../modules/request.md#compose-nested-resource-paths) shows
this in full, and `Request.setPath` replaces what a constructor wrote.

## Schemas work with what is already there

A header or query schema now [states the shape of its
group](../modules/request.md#a-schema-states-the-shape-of-its-group), instead of owning it: once any
schema is bound to headers or query, every header or query field the request declares must be a name
some schema allows. A raw value under such a name is a default, schemas stack, and `Request.unbind`
starts a group again. So shared headers and typed fields can sit on one request, and a variant can
add to a typed group.

A schema-backed input also takes [either side of its
schema](../modules/request.md#a-schema-has-two-sides), or a mix by field. A plain object works for a
`Schema.Class`, a field with a constructor default can be left out, and a query can carry a `Date`.
`Request.setQuery` and `Request.setHeader` also take a plain object for several fixed fields.

## A location can be known late

`Request.baseUrl` also takes an Effect, so a service or a `Config` value can supply a location that
is not known when a request is defined, and leaving that service out is a compile error.
`Request.mapBaseUrl` extends a prefix you only have as a value, and `transformClient` now receives
the attempt number, so a retry can go to another server. [Find the API when the application
starts](../recipes.md#find-the-api-when-the-application-starts) puts these together.

## What a request declares reaches the client

A declared `Content-Type` or `Content-Length` now takes effect, `Request.removeHeader` stops an
automatic header, a header name keeps its spelling, a constructor query keeps its text, a fragment
stays on the request, and any method can carry a body.

The library passes the request you declared to the HTTP client you chose, and [its promise stops
there](../limits.md#paths-and-other-requests-passed-on-as-written). The client may rewrite or refuse
it, and a server may read it differently. So a client can still refuse what the library used to
refuse for you.

### Raw values beside a schema

A header or query schema used to replace every raw value with no warning. A raw value under a name
no schema allows is now `Request.InvalidRequest`, including one written in the constructor. It
compiles, then fails on every run, before anything is sent. The error names the fields.

**Search for** `Request.query` and `Request.headers` on a request that also has `setQuery`,
`appendQuery`, `setHeader`, `appendHeader`, a `?` in its constructor, or a shared transform that
sets any of those.

```ts [0.1]
const search = Request.get("https://api.example.test/search?lang=en").pipe(
  Request.setHeader("authorization", "Bearer token"),
  Request.query(Schema.Struct({ q: Schema.String })),
  Request.headers(Schema.Struct({ "x-trace": Schema.String })),
);
// ?q=ada with x-trace. lang and authorization were dropped with no error.
```

Those values never went out, so decide whether they should. To send them, let the schema allow them:

<<< ../../examples/migration-0-2.ts#shape-allow

To keep what went out on `0.1`, remove them:

<<< ../../examples/migration-0-2.ts#shape-remove

A raw setter after a schema used to be a compile error. It now compiles, and a raw edit of a field
the schema always writes is `InvalidRequest`. Header and query schemas also add `InvalidRequest` to
the request's error type, which matters to an annotation that spells that type out.

### Declared headers

A declared `Content-Type` or `Content-Length` used to be replaced by the body's value or dropped,
wherever it stood, and `Request.removeHeader` could not stop an automatic header. Both now take
effect, from a raw setter or a header schema, before or after the body.

**Search for** `content-type`, `content-length` and `accept`, in any spelling, in `setHeader`,
`appendHeader`, `removeHeader` and header schemas.

```ts [0.1]
const sendJson = Request.post("https://api.example.test/things").pipe(
  Request.setHeader("content-type", "application/vnd.example+json"),
  Request.body(Body.json),
);
// content-type: application/json. The declared value was replaced.
```

On `0.2` the declared value goes out. If that is what the service expects, change nothing. To keep
what went out on `0.1`, delete the declaration:

<<< ../../examples/migration-0-2.ts#header-automatic

A `Request.removeHeader("accept")` that did nothing now removes the automatic `Accept`, so delete it
if you want that header. A declared `Content-Length` that disagrees with the body is passed on, and
a client can fail or stall on it.

### Query text in a constructor

A constructor's query used to be decoded and rendered again. It now stays as you wrote it until
something edits that entry or a schema covers it:

| Written       | `0.1` passed on  | `0.2` passes on |
| ------------- | ---------------- | --------------- |
| `/x?a=1;b=2`  | `/x?a=1%3Bb%3D2` | `/x?a=1;b=2`    |
| `/x?q=a+b`    | `/x?q=a%20b`     | `/x?q=a+b`      |
| `/x?a=1&&b=2` | `/x?a=1&b=2`     | `/x?a=1&&b=2`   |
| `/x?`         | `/x`             | `/x?`           |

**Search for** a `?` in the text given to `Request.make` and the method helpers, and for a custom
`UrlEncoding.query`, which no longer receives entries kept as written.

Text the library used to escape is no longer escaped, so declare a value that needs escaping.

Before:

```ts [0.1]
const findAda = Request.get("/search?q=Ada Lovelace");
// /search?q=Ada%20Lovelace
```

### A body on GET or HEAD

`Request.compile` no longer refuses a body on GET or HEAD. The client decides, and `fetch` refuses
one, so with Fetch the failure moves from `Request.InvalidRequest` to a transport failure.

### Providers and extensions

Most applications can stop here. The changes below affect code that implements an HTTP provider or
reads the library's lower-level types.

**A provider built with `HttpClient.makeWith`.** The compiled URL no longer holds a fragment, which
moves to `request.hash`. A `#` in a base URL or in `Request.path` output used to take the query into
the fragment, as `/users/1#top?f=xml`. The query now goes first. A fragment in a constructor used to
be discarded and now reaches the client, and a custom `UrlEncoding.join` receives the base and path
without fragments. **Search for** `HttpClient.makeWith`, a custom `join`, and a `#` in your URLs.

Before:

```ts [0.1]
const targetOf = (native: HttpClientRequest.HttpClientRequest) => native.url;
```

After:

<<< ../../examples/migration-0-2.ts#fragment-provider

used to be lowercase. Comparing names still folds case inside the library, and `fetch` still sends
lowercase names. **Search for** `headerLines` compared with a lowercase name.
