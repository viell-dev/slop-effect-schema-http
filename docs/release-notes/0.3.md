# What's in 0.3

Effect Schema HTTP 0.3 makes an input keep what the caller gave. A field no longer goes because of
the order of a union's members, and a field a schema cannot keep is now an error, not a silent drop.
A raw edit that could never reach the client is refused for more of the fields a schema always
writes.

`0.3.0` is a breaking release, and it is about to be published. Until then `0.2.0` stays the current
version. The [version policy](../versions.md) explains installation and updates, and the [detailed
changelog](../changelog.md) records individual changes. Read the next section before you update.

## Check your unions first

A call that sent a request on `0.2.0` can now fail at run time, and whether it does depends on the
values. The definition compiles and has not changed. The same code sends one call and refuses the
next, so start here.

This definition compiles on both versions:

```ts [0.2]
const Filter = Schema.Union([
  Schema.Struct({ owner: Schema.String }),
  Schema.Struct({ team: Schema.String }),
]);
const search = Request.get("https://api.example.test/things").pipe(
  Request.query(Filter),
);
```

| The caller gives                 | `0.2` sends                   | `0.3`                             |
| -------------------------------- | ----------------------------- | --------------------------------- |
| `{ owner: "ada" }`               | `?owner=ada`                  | The same                          |
| `{ team: "core" }`               | `?team=core`                  | The same                          |
| `{ owner: "ada", team: "core" }` | `?owner=ada`, and `team` goes | A `SchemaError`, and nothing sent |

On `0.2`, Effect took the first member that fitted and stripped what it did not state, so `team`
went with no error. No member can hold both fields, and the types allow that value, so the library
will not choose for the caller. The failure names the field and leaves out its value:

```text
No union member holds this field with the rest of the value
  at ["team"]
```

A `SchemaError` was already in the request's error type, so the compiler says nothing. It fails only
for the values that reach it, so a test that never passes both fields passes on both versions, and
the first call that does can be in production.

### Find them by reading

Read your schemas, because nothing else finds these. Go through what you give to `Request.query`,
`Request.headers`, `Request.path`, `Body.jsonSchema` and `Body.encodeSchema`, and follow any schema
that comes from another file.

**Search for** `Schema.Union` over objects, including classes, at any depth: in a field, a list, a
record, a `Map` or an `Option`. For each one, ask whether a value can hold fields from two members.
Look for:

- **A value built from several sources,** such as form state, where both fields can be filled in.
- **A wide object given to a union of narrow views,** such as a whole user under a union of `{ id }`
  and `{ name }`. It used to be cut down to the first member that fitted, and now it is refused.
- **A field a wider member refuses.** Under a union of `{ owner }` and
  `{ owner, limit: Schema.FiniteFromString }`, `{ owner: "ada", limit: "many" }` used to lose
  `limit` and send `?owner=ada`. Now the value is refused, because a field the schema states would
  go.

In a body, the failure names the whole path, such as `["filter"]["team"]`.

These do not fail, and need no change:

- **A key no member states.** It is stripped, as a struct strips it. The types refuse it in a
  literal.
- **A key set to `undefined`.** It holds no value to lose, so `{ owner: "ada", team: undefined }`
  goes out as `?owner=ada`.
- **A key only a member with another tag states.** The tag has already chosen, so `{ kind: "b", x }`
  goes out as `{ kind: "b" }` where only the `"a"` member has `x`.
- **A field a stacked schema takes.** A union of `{ owner }` and `{ team }` stacked with `{ team }`
  sends both, in either order. On `0.2` it failed in one of those orders.

## A union keeps what the caller gave

The same change has a second half, which sends more instead of failing. A member that keeps every
field now wins over an earlier one that would strip one, on either side of the schema and at any
depth. So a wider member no longer has to go first.

Under a union of `{ a }` and `{ a, b }`:

| The request has | The caller gives     | `0.2` sends | `0.3` sends |
| --------------- | -------------------- | ----------- | ----------- |
| Nothing else    | `{ a: "x", b: "y" }` | `?a=x`      | `?a=x&b=y`  |
| A raw `?b=1`    | `{ a: "x", b: "y" }` | `?a=x&b=1`  | `?a=x&b=y`  |
| A raw `?b=1`    | `{ a: "x" }`         | `?a=x&b=1`  | The same    |

This works in headers, query, path and bodies. It also applies to a class and its subclass, where a
subclass's instance used to lose its own fields under its base class, and to a union with a record,
which now takes the fields a struct before it would strip.

## What your client does

The library passes a request to the client and reads what the client gives back, and [its promise
stops there](../limits.md#what-a-client-does-with-a-request). This project's integration tests
measured what clients do at that boundary, and the guides now say so. None of this changed in `0.3`,
and it is worth reading if you write from a browser or retry:

- [`Policy.none` is one attempt by the library, not one
  send](../limits.md#one-attempt-can-reach-a-server-twice). When a reused connection ends with no
  response, Chromium sends a POST again by itself, so one attempt can make two commits.
- [A body cut off after its headers](../limits.md#a-body-cut-off-after-its-headers) is not retried
  through `fetch` and is retried through a provider such as Node's `http`, so one cut POST can
  duplicate through one provider and not another.
- [A compressed body that stops early](../limits.md#a-compressed-body-that-stops-early) can be a
  partial body and a success.
- [A redirected response can stay open](../limits.md#a-redirected-response-can-stay-open) until
  garbage collection, if nothing reads it.

### Fields that now go out

A field a union used to drop now reaches your service. That is what the caller gave and what the
schema states, but it is a request your server has not had from this code before.

**Search for** a union of objects where a later member states more than an earlier one, and for a
value that holds more than you meant to send, such as a whole record passed to a union of its views.

```ts [0.2]
const NarrowFirst = Schema.Union([
  Schema.Struct({ owner: Schema.String }),
  Schema.Struct({ owner: Schema.String, team: Schema.String }),
]);
const search = Request.get("https://api.example.test/things").pipe(
  Request.query(NarrowFirst),
);
// { owner: "ada", team: "core" } asked for ?owner=ada. team was dropped with no error.
```

If that field should go out, change nothing. To keep what went out on `0.2`, take the field out
before the schema sees it:

<<< ../../examples/migration-0-3.ts#union-narrow

A union member that is `Schema.Struct({})` takes any value and keeps it, so it now wins over a
member that would strip a key, and that key goes out. Give it the fields you mean, or remove it.

### A raw edit of a field with a decoding default

A raw edit after a schema, of a name it always writes, was already an error. A field with a decoding
default got past that check, because it is optional on the encoded side, although the schema writes
it all the same. The edit never went out, with no error. It is now `Request.InvalidRequest` on every
run, whatever the input, before anything is sent. The error names the field.

**Search for** `withDecodingDefaultKey`, `withDecodingDefault`, `withDecodingDefaultTypeKey` and
`withDecodingDefaultType` in header and query schemas, then for `setQuery`, `appendQuery`,
`removeQuery`, `setHeader`, `appendHeader` and `removeHeader` after that schema, including in a shared
transform.

```ts [0.2]
const Paging = Schema.Struct({
  limit: Schema.FiniteFromString.pipe(
    Schema.withDecodingDefaultKey(Effect.succeed("25")),
  ),
});
const listThings = Request.get("https://api.example.test/things").pipe(
  Request.query(Paging),
  Request.setQuery("limit", "50"),
);
// { query: {} } asked for ?limit=25. The edit never went out.
```

default with the `omit` encoding strategy behaves as it did. Two gaps remain, and neither fails: a
decoding default under `Schema.encodeKeys`, and an optional key with
`Schema.withConstructorDefault`, each still lose such an edit with no error.
