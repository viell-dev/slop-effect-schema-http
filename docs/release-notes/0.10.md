# What's in 0.10

TypeScript change only: 0.8 retained outer encoded names, while this release retains whole encoded
shapes below unchanged outer names. Calls already accepted at runtime now compile. It does not
extend 0.9's constructor-default validation.

`0.10.0` is a breaking release because a helper accepting `Request.Input` can now receive encoded
nested names that the type previously hid. Give decoded-only helpers an explicit input shape or
handle the actual alternatives. The [version policy](../versions.md) covers updates, and the
[changelog](../changelog.md) records the changes.

Compare the [related release family](./index.md#schema-input-hardening); use [Schema-backed
input](../schema-input.md) and [Schema-backed groups](../schema-groups.md) for today's contract and
active limits. The running schema below makes the changed route, container or layer directly
comparable with the previous release.

## Give a helper its own decoded input shape

A helper taking `Request.Input<typeof Nested>` can no longer assume that `input.filter.limit`
exists: its filter may use `page_size`. The compiler reports that property access with `TS2339`.

If the helper accepts decoded application values, declare those names explicitly. This mapping also
states the application's fallback policy instead of expecting the input type to choose it:

<<< ../../examples/migration-0-10.ts#helper-input

`Request.compile(search, { filter: { limit: "05" } })` prepares `/05`; an empty filter prepares
`/25`. The mapping still passes its result through the schema. If a helper accepts either side,
handle the actual decoded and encoded alternatives rather than assuming the decoded property is
available. The earlier [0.8 helper migration](./0.8.md) applies to outer aliases as well.

## Reading and remaining limits

This repair retains whole schema sides. Fieldwise mixing in the static type remains one level deep;
it does not recursively rebuild fields or add a new mixing policy. Preparation still tries the
decoded constructor first, then whole decoding, then fieldwise recovery. Existing defaults,
validation, service requirements and selection priority keep their behavior.

Inside an opaque value, the schema's own reading still applies. For example, accepting the encoded
type of a `Schema.ReadonlyMap` does not force encoded reading of its contents. An inner
`{ term: "x", page_size: "05" }` can fit the map's decoded constructor by losing the alias; typing
alone does not change that route. Supply decoded contents such as `{ term: "x", limit: "05" }` for a
predictable decoded route.

The bounded [0.9 encoded-default repair](./0.9.md) and its limits still apply. In particular, on
0.10, constructor failure followed by member or fieldwise recovery could still let an invalid
encoded alias take a default. [0.11](./0.11.md) now narrows eligible final fieldwise routes without
replaying effects; member-constructor and unsupported routes remain under
[#170](https://github.com/viell-dev/slop-effect-schema-http/issues/170). Use decoded input or a
named decoded-input mapping for those schemas. The proof also remains at the root: a nested optional
finite-number `limit` with a constructor default can still turn `filter: { page_size: "many" }` into
that default on both 0.9 and 0.10. Corrected typing does not repair that visible nested runtime
defect. [0.12](./0.12.md) repairs eligible direct-object paths after successful initial whole
construction and strict writing. Conflicting aliases and the broader [schema/raw-input
limits](https://github.com/viell-dev/slop-effect-schema-http/issues/143) remain separate from this
type repair. [Limits and recovery](../limits.md) records the supported checks and workarounds.
