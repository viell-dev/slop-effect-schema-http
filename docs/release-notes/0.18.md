# What's in 0.18

Effect Schema HTTP `0.18.0` changes what schema-backed request input sends in four cases. A request
union with a built-in `Schema.Void` member now keeps or refuses the fields of a supplied object
instead of discarding it as `null`. An object read by `Schema.Struct({})` keeps its keys when
preparation reads the whole value strictly. Preparation stops sending a list as an object keyed by
its indexes. Constructor-alias validation now also covers encoded primitive and array-shaped union
members, so an invalid encoded alias beside `Schema.FiniteFromString` or in a one-or-many union
refuses instead of being replaced by a default. Formerly successful calls can fail or send a
different body, so this is a breaking release.

The Void change extends the existing rule that a union keeps what the caller gave
([#143](https://github.com/viell-dev/slop-effect-schema-http/issues/143)) to Void members, and the
empty-struct change fixes that strict reading where it dropped keys. The alias change extends the
[0.16](./0.16.md#validate-optional-object-alternatives) and [0.17](./0.17.md) constructor-alias rule
and does not finish [#170](https://github.com/viell-dev/slop-effect-schema-http/issues/170). The
list change is a separate fix, of the last field-by-field reading
([#237](https://github.com/viell-dev/slop-effect-schema-http/issues/237)). Another fix reports a
query or header schema that encodes no field record as `InvalidRequest` instead of a defect
([#236](https://github.com/viell-dev/slop-effect-schema-http/issues/236)).

Use [Schema-backed input](../schema-input.md) for the complete current contract and retained limits.
The [changelog](../changelog.md) also records the development tool updates that this release
carries.

## Keep fields beside Void

Built-in `Schema.Void` accepts any value and returns `undefined`. Effect takes the first member of a
union that fits, so Void could take a supplied object before an object member read it, and its
writer could discard the object again. This filter reads finite numbers from text, renames the field
and gives construction a default; the body is either nothing or a filter:

<<< ../../examples/migration-0-18.ts#void-kept

On 0.17, all four calls prepared `null`. On 0.18, `encoded` and `decoded` prepare
`{"page_size":"5"}`, and `invalid` fails with `SchemaError` at `["page_size"]` before dispatch.
`empty` still prepares `null`: an object with no field has nothing to lose, so Void keeps Effect's
first-fit reading. With Void placed last, 0.17 already sent the decoded value but discarded both
encoded ones; they now behave as above.

The strict read declines Void for an object with a defined enumerable own field, or a list with a
defined own cell. It first removes keys no member states, so an object with only such keys, such as
`{ other: 1 }`, also keeps first fit: with Void placed first it still prepares `null`. A union of
Void and plain empty structs alone keeps first fit as well:
`Union([Schema.Struct({}), Schema.Void])` keeps `{ tag: "a" }` and
`Union([Schema.Void, Schema.Struct({})])` prepares `null`, both as on 0.17. The strict write
declines Void for every object or list, including one whose fields decoded to `undefined`. This
applies in any-of unions with an object or list member, at any depth, to annotated and checked Void,
and through unencoded any-of unions inside the union. Such a Void also counts as an alternative that
cannot hold an object in the [0.16 constructor-alias
rule](./0.16.md#validate-optional-object-alternatives), which is why the invalid alias refuses
instead of being replaced by the default. With Void placed last, the refusal names the alias, such
as `["filter"]["page_size"]`, even when a valid decoded sibling such as `n: 1` makes the parent read
field by field; on 0.17 that value prepared `{"n":"1","filter":null}`.

A value that mixes the two sides by depth can refuse beside Void:

With the object member first, the strict read treats a key set to `undefined` as absent:

<<< ../../examples/migration-0-18.ts#void-undefined

## Keep keys under an empty struct

`Schema.Struct({})` alone keeps every key of the object it reads. When preparation reads the whole
value strictly, as it does under a renamed field or an object union, 0.17 dropped those keys:

<<< ../../examples/migration-0-18.ts#empty-struct

On 0.17, `labelled` prepared `{"labels":{},"wire_title":"item"}`. On 0.18 it prepares
`{"labels":{"tag":"a"},"wire_title":"item"}`. The keys are kept at any depth within the chosen union
member when every object candidate at that value states no property or index signature, as in
`Union([Schema.Struct({ e: Schema.Struct({}) }), A])` with
`A = Schema.Struct({ a: Schema.String })`, which now sends `{"e":{"tag":"a"}}` for
`{ e: { tag: "a" } }`. A `Schema.Struct({})` query or header binding still states no names, but a
union of only empty structs there now sends a supplied key too:
`Request.query(Schema.Union([Schema.Struct({}), Schema.Struct({})]))` with `{ tag: "a" }` sends
`?tag=a`, where 0.17 sent no query.

## Report non-object query and header groups

JavaScript, casts and `Schema.Any` can bypass the TypeScript requirement that a query or header
schema encodes a group of fields. On 0.17, a header record with a number value, or a group that
encoded no object, could stop preparation with a `TypeError` defect such as
`value.map is not a function`. On 0.18 it fails with `InvalidRequest` before dispatch, after any
lost input fields are reported.

Two header inputs that 0.17 sent now fail with `InvalidRequest` too: a list of numbers, as in
`{ "x-count": [1, 2] }`, and a pair with a number value, as in `[["x-count", 1]]`. On 0.17 a header
schema such as `Schema.Any` wrote their numbers as header values. The input types already reject
both, so only casts and JavaScript reach them. Supply header values as text.

## Keep a list a list

When every whole reading of a value failed, preparation's last route read it field by field,
starting from a copy. That copy turned a list into an object keyed by its indexes, which a record
member could then take:

<<< ../../examples/migration-0-18.ts#list-schema

<<< ../../examples/migration-0-18.ts#lists

On 0.17, `wrongItem` prepared `{"0":{"limit":5}}`. On 0.18 it fails with `SchemaError` at
`[0]["limit"]`, as `Schema.Array(Plain)` alone does. The valid list and the object keep their
results. The type already excludes `[{ limit: 5 }]`; external data and casts can still supply it.

The field-by-field route no longer copies an actual list, at any depth. That covers bodies, paths,
nested fields and a struct member with index-like fields, and reading a query or header group
supplied as a list of pairs. Beside a record of string lists, the pair list `[["a", "b", "c"]]`,
whose item is not a pair, prepared the query `?0=a&0=b&0=c` on 0.17 and now refuses. Union members
are still tried one by one.

## Refuse a list given to an object schema

The largest change for ordinary schemas is a list given to a struct, class or record alone. It now
fails with `SchemaError` `Expected object`, as Effect's object schemas and the input types do:

<<< ../../examples/migration-0-18.ts#object-only

On 0.17, `listForRecord` prepared `{"0":{"limit":"x"}}` and `listForStruct` prepared `{}`: the
struct read the index-keyed copy and dropped its keys. A class behaved like the struct. A
constructor default could fill the result, so `Filter` given `[]` prepared `{"page_size":"25"}`. A
query group also read the copy: `Request.query(Plain)` given `[["limit", "x"]]` prepared `/plain`
with no query. Each now refuses. Only casts and JavaScript reach these inputs. If a service expects
the index-keyed object, build it explicitly: `spread` prepares `{"0":{"limit":"x"}}` on both
releases.

## Strip keys a list item does not state

Beside a record, a list item with a key the list member does not state now refuses:

<<< ../../examples/migration-0-18.ts#unstated-keys

On 0.17, `unstated` prepared `{"0":{"limit":"x","extra":1}}`. On 0.18 it fails with `SchemaError` at
`[0]["extra"]`. `Schema.Array(Plain)` alone strips `extra` and writes `[{"limit":"x"}]`, so this
refusal is a remaining defect
([#243](https://github.com/viell-dev/slop-effect-schema-http/issues/243)), not the intended result.
Validate the list with its own schema first: `stripped` prepares `[{"limit":"x"}]`. An encoded-only
key such as `[{ page_size: "05" }]` behaves the same way.

## Validate aliases beside encoded and array-shaped members

0.17 validated an invalid encoded alias only beside unencoded primitive alternatives. Beside an
array or tuple member, or an encoded primitive such as `Schema.FiniteFromString`, the alias was
still replaced by the constructor default. A union of the filter above and a list of filters shows
the array-shaped case:

<<< ../../examples/migration-0-18.ts#alias-schema

<<< ../../examples/migration-0-18.ts#one-or-many

On 0.17, `invalidOne` prepared `{"page_size":"25"}` and `invalidMany` prepared
`[{"page_size":"25"}]`: the caller's `"many"` was replaced by the default. On 0.18 both fail with
`SchemaError` before dispatch, with the message `Filter` alone gives, such as
`Expected no excess property at ["page_size"]`. Valid values on either side and omissions keep their
results.

An array or tuple member cannot hold an object, so beside an object cell it now counts as an
alternative that cannot hold one, like a primitive. For a list cell, the union follows its one
member that can read a list when every other member refuses lists: a primitive, a guarded Void, or
an object that states a field or index signature, such as a record or `Cursor`. So
`Union([Schema.Array(Filter), Cursor])` refuses `[{ page_size: "many" }]` too, where 0.17 prepared
`[{"page_size":"25"}]`. The rule applies at the root, in fields and in array elements.

The [encoded alternative](./0.17.md#bounds-and-remaining-work) that 0.17 left outside the rule now
refuses as well:

<<< ../../examples/migration-0-18.ts#encoded-primitive

On 0.17, `invalidCount` prepared `[{"page_size":"25"}]`. On 0.18 it refuses at `[0]["page_size"]`,
and `counts` still prepares `["7",{"page_size":"5"}]`. An encoded member counts when its type and
every encoding stage are primitive alternatives joined by plain transformations, as in
`Schema.FiniteFromString`, `Schema.NumberFromString` or a codec from text to nullable text.

## Supply one side throughout a list

The additional validation reads the whole value, so beside these members it also reaches lists that
mix encoded-only and decoded-only items, even when every item is valid:

<<< ../../examples/migration-0-18.ts#list-sides

On 0.17, `mixedItems` prepared `[{"page_size":"25"},{"page_size":"7"}]`: the valid `"05"` was
replaced by the default. On 0.18 it fails with `SchemaError` at `[1]["limit"]`. The input type
accepts this list, so typed code can reach the refusal. 0.17 replaced the alias in either order:
`[{ limit: 1 }, { page_size: "30" }]` prepared `[{"page_size":"1"},{"page_size":"25"}]`, and on 0.18
it refuses at `[0]["limit"]`. `encodedItems` and `decodedItems` both prepare
`[{"page_size":"5"},{"page_size":"7"}]`.

When items come from different sources, decode the wire items with the schema and supply decoded
values throughout:

<<< ../../examples/migration-0-18.ts#decode-first

`withStored([{ page_size: "05" }])` prepares `[{"page_size":"5"},{"page_size":"7"}]`. An invalid
stored item fails in `readFilters`, before preparation.

## Account for both names in a list

An item that gives both names beside an encoded-only item is now read by its encoded name:

<<< ../../examples/migration-0-18.ts#dual-names

Since 0.19 a field given under both its names refuses, as [0.19's
rule](../schema-input.md#constructor-default-validation) describes. The rest of this section is what
this release did.

This nonliteral input typechecks. On 0.17, `conflicting` prepared
`[{"page_size":"1"},{"page_size":"25"}]`; on 0.18 it prepares
`[{"page_size":"2"},{"page_size":"25"}]`. The encoded-only second item enables whole decoding, which
reads the encoded name, as [0.16 described](./0.16.md#account-for-conflicting-names) for other
containers. This remains a [conflicting-alias limit](../schema-input.md#active-limits-and-recovery),
not a check that both values agree. Give each item one name: `oneName` prepares
`[{"page_size":"1"},{"page_size":"25"}]`.

## Update

1. Search input schemas for `Schema.Void` in a union beside an object or list, including annotated,
   checked and nested forms. Calls that sent `null` for a supplied object now send its fields, or
   fail with `SchemaError` when an encoded alias is invalid. Check that the service accepts them.
2. Beside Void, in either member order, use one side's names throughout a value and give each field
   one name. Mixed values and objects giving both names now fail before any request.
3. Check object constructor defaults beside Void, which are now sent, and object-first unions given
   only keys set to `undefined`.
4. Check object members beside Void whose values may not encode, such as `Schema.Unknown` metadata
   holding a `Date`. Such calls now fail with `SchemaError` instead of sending `null`; supply
   encodable values.
5. Check fields read by `Schema.Struct({})`, and unions whose only object members are empty: their
   keys are now sent. Remove keys the service should not receive.
6. Lists that went out as index-keyed objects beside a record or struct member now fail with
   `SchemaError`, and so does a list given to a struct, class or record alone. Correct the items or
   supply an object, building it explicitly when the service expects index keys.
7. Strip list item keys the list member does not state before preparation, for example by decoding
   with the list schema.
8. Search input schemas for encoded primitive members such as `Schema.FiniteFromString` or
   `Schema.NumberFromString`, and for unions of a list member with an object, record or Void, beside
   a renamed field with a constructor default. Calls that sent invalid encoded aliases there now
   fail with `SchemaError` before any request. Correct the input, or validate it first and supply
   decoded values.
9. Lists there that mix encoded-only and decoded-only items now fail too. Supply every item on one
   side, or decode the wire items first.
10. An item giving both names beside an encoded-only item is now read by its encoded name. Give each
    item one name.
11. Supply header values as text. A cast or `Schema.Any` header schema that encodes numbers now
    fails with `InvalidRequest`.

## Bounds and remaining work

Void protection applies to built-in Void beside a visible object or list member in an any-of union.
Standalone Void, class-backed alternatives and class fields, opaque declarations, suspensions,
encoded member unions, `oneOf` unions and custom discarding transformations can still discard
values. A JavaScript list whose cells are all non-enumerable, beside a struct and Void, can still be
written as `null`. When the object member cannot write a value and another member can, the fallback
can choose that member even where it drops supplied fields
([#250](https://github.com/viell-dev/slop-effect-schema-http/issues/250)). Leave Void out of input
schemas that rely on those shapes.

A union that mixes an empty struct with a member that states fields still strips the keys no member
states: `Union([A, Schema.Struct({})])` prepares `{"a":"x"}` for `{ a: "x", z: 1 }`, as on 0.17
([#249](https://github.com/viell-dev/slop-effect-schema-http/issues/249)).

The list rule covers only the copy the field-by-field route would make. Effect's own readings still
apply: `Schema.Struct({})` keeps a list as it is, and an empty `Schema.Class` builds an instance
keyed by a list's indexes. A constructor default can still replace an invalid item under a parent
read field by field ([#241](https://github.com/viell-dev/slop-effect-schema-http/issues/241)), and
writing a query or header group can still send a pairs list without an iterator prototype under its
indexes ([#242](https://github.com/viell-dev/slop-effect-schema-http/issues/242)).

Since 0.19 [0.19's rule](../schema-input.md#constructor-default-validation) replaces the proof
below, so only the recovering member's own reading remains of these limits. In this release the
alias proof stops at middleware-encoded alternatives, because middleware such as
`Schema.catchDecoding` can turn a failed read into a value. For a list cell it stops at a union with
`Schema.Struct({})`, a second member that reads lists, an encoded list member, or a declaration such
as `Schema.Class` or `Schema.Option` beside the list member. The schema's own selection decides
there:

<<< ../../examples/migration-0-18.ts#proof-stops

`stillRecovered` prepares `"0"`, the recovering member's own reading, and `stillListed` prepares
`[{"page_size":"25"}]`, both as on 0.17. Lists behind a custom prototype under a one-or-many union
also stay outside the proof. A member union value used both where its Void is guarded and where it
is not, such as one also placed under a `oneOf` union, gets the grouped proof at neither use; build
a separate member union for each use. Under these unions, an invalid alias supplied together with
its decoded name, such as `{ limit: 5, page_size: "many" }`, still prepares `{"page_size":"5"}`.
Beside Void, an object giving both names refuses in either member order, as
`{ limit: 5, page_size: "5" }` does, where 0.17 prepared `null`.

[Active limits](../schema-input.md#active-limits-and-recovery) lists the remaining cases under #143
and #170.
