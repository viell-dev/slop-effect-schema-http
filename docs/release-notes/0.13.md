# What's in 0.13

Effect Schema HTTP `0.13.0` validates nested encoded aliases through eligible parent unions before a
constructor default replaces them. In the covered paths, invalid input now fails with `SchemaError`
before rendering or dispatch. This is a breaking runtime change.

The [version policy](../versions.md) covers updates, and the [changelog](../changelog.md) records
the changes. The [0.12 migration](./0.12.md) explains the earlier direct-object extension; this
release adds parent unions with unambiguous field declarations.

Both tagged branches use `Filter`. The proof keeps all parent member names in its caller evidence,
but follows a field only when every declaring member gives it the same schema. It does not merge
distinct declarations by comparing their shapes or sampling their transformations. Composing schemas
can declare one JavaScript field twice, including numeric `1` and text `"1"`; those declarations
must agree too. Distinct field schemas can remain outside this bounded check, even if their shapes
look alike.

## Bounds and remaining work

The extension requires finite closed, untransformed object/union ancestors and one field schema at
each step. Every parent union member must itself provide such an object/union view; primitive and
null alternatives remain outside this extension. Other closed members can omit a field; they do not
invent ownership. The original initial whole construction and strict writer must actually succeed.
Stable own-data caller links must reach the same encoded-only terminal field written in that output.
One coherent witness stays fixed through whole decoding and the existing loss/sibling checks.

Metadata inspection runs no checks, defaults or suspensions. Whole decoding can repeat schema checks
and services; defaults and writers may already have run before refusal, and their effects are not
undone. Construction is not replayed. Actual member-fieldwise routes can correctly consume nested
aliases and do not establish this constructor-only proof. Existing strict-success, root proof and
writer-fallback routes retain their priority.

The ambiguity guard also applies to direct object ancestors. With conflicting numeric `1` and string
`"1"` declarations, a call refused in 0.12 can now succeed with a generated default in 0.13. For
example, the [typed literal-Record reproduction in
#170](https://github.com/viell-dev/slop-effect-schema-http/issues/170#issuecomment-6733524389)
changes from `SchemaError` to `/limit/25` for supplied `wire: "many"`, directly or below an
unchanged `page` field. The earlier refusal relied on a field declaration that does not establish
unambiguous ownership. Default substitution remains a kept-or-refused defect; this guard correction
does not repair it. Validate and map input to decoded names before preparation, or supply validated
decoded values, for these schemas.

Distinct field declarations can still substitute a default for invalid encoded input. Arrays,
open/transformed/class/declaration/suspended parents, ambiguous terminal names, inherited/accessor
links, iterable/changing objects and unsupported member/fieldwise phases remain bounded under
[#170](https://github.com/viell-dev/slop-effect-schema-http/issues/170). Use decoded values or a
validated decoded mapping for affected schemas. Opaque values retain their schema's own reading. The
broader [schema/input gaps](https://github.com/viell-dev/slop-effect-schema-http/issues/143) remain
open. [Limits and recovery](../limits.md) records the supported checks and workarounds.
