# What's in 0.19

Effect Schema HTTP `0.19.0` applies one rule throughout request preparation: a supplied value is
kept, or the request is refused before dispatch with an error naming it. Earlier releases applied it
case by case. Three layers change:

- **Reading.** Every route accounts for what it was given, at the root as in a field, so a default
  never takes the place of a supplied field. Open and empty-struct union members keep the keys they
  hold, and built-in `Schema.Void` takes only `undefined`, `null` or an object or list that holds
  nothing.
- **Writing a schema.** A value that cannot be written strictly goes through the union member that
  holds it, and a member that would drop a supplied field is refused.
- **Writers.** JSON, form, text, query and header writers refuse a value they would leave out or
  replace, such as `NaN` or a `Map`.

Formerly successful calls can fail or send a different request, so this is a breaking release. Calls
that supply decoded values, or one complete encoded side, of plain data that the wire can represent
send what they sent on 0.18, apart from the union results and writer refusals below. A key the
schema does not state is still left out, as Effect leaves it out, and a value that is not plain data
still reads and writes as Effect reads and writes it. [The input reference](../schema-input.md)
states both rules.

The constructor-default repair that 0.9 to 0.18 extended shape by shape is finished with this
([#170](https://github.com/viell-dev/slop-effect-schema-http/issues/170)), and so are the recorded
preservation gaps of [#143](https://github.com/viell-dev/slop-effect-schema-http/issues/143) and
[#243](https://github.com/viell-dev/slop-effect-schema-http/issues/243). What the library cannot see
is listed under [Limits](../schema-input.md#active-limits-and-recovery). The
[changelog](../changelog.md) has every change with its issue.

`kept` prepares `{"n":"1","items":[{"page_size":"5"},{"page_size":"25"}]}` on both versions. The
others refuse on 0.19 with `SchemaError`, naming the field:

| Call         | 0.18 prepared                                    | 0.19                                                 |
| ------------ | ------------------------------------------------ | ---------------------------------------------------- |
| `invalid`    | `{"n":"1","items":[{"page_size":"25"}]}`         | refused at `["items"][0]["page_size"]`               |
| `bothInItem` | `[{"page_size":"2"},{"page_size":"25"}]`         | refused at `[0]["page_size"]` and `[1]["page_size"]` |
| `bothNames`  | `{"page_size":"5"}`                              | refused at `["page_size"]`                           |
| `inRecord`   | `{"a":{"page_size":"1"},"b":{"page_size":"25"}}` | refused at `["b"]["page_size"]`                      |

These calls type-check, and refuse when prepared. A field given under both its names refuses even
where the two agree. A list, tuple or record is read as one value, so its items are all on one side,
and the refusal names each item on the other: `bothInItem`'s second item and `inRecord`'s `b` are
valid alone. A decoded name below a field given by its written name refuses too. A schema's error
writes a position as `at ["page_size"]`, and the library's own writers write it as `$["page_size"]`.
A decoding default no longer fills a field that a decoder stripped: `Schema.Array(Page)` with a
decoding default sent `30` for the valid `[{ limit: 5 }, {}]` and now refuses it, because a list is
decoded as a whole.

## Write a value through the member that holds it

<<< ../../examples/migration-0-19.ts#write

On 0.18 `dated` prepared `{"title":"a"}`: `Note` could not write the `Date`, so the write fell back
to `Title`, which dropped it. On 0.19 it fails with `Note`'s own error at `["meta"]`. Encode the
value with a schema, such as `Schema.Date`, instead of `Schema.Unknown`.

A class instance with a member of its own cannot be written strictly. On 0.18 that made the write
beside it take each union's first member that fits, so `besideClass` refused, and other calls lost a
field or sent a default. On 0.19 each union is still written by a member that holds the value, and
`besideClass` prepares `{"f":{"title":"a","n":1},"c":{"a":"x"}}`.

## Expect open members to keep their keys

An empty struct, and `Schema.Unknown`, `Schema.Any` or `Schema.Object`, keep every key of a value
they read. Beside members that state fields, they now do so at every depth:

<<< ../../examples/migration-0-19.ts#open

| Call    | 0.18                  | 0.19                    |
| ------- | --------------------- | ----------------------- |
| `tag`   | `/things?page_size=5` | `/things?limit=5&tag=a` |
| `below` | `{"b":{"a":"x"}}`     | `{"b":{"a":"x","z":1}}` |

The open member takes the whole value as given, so a renamed field beside the extra key keeps its
decoded name. Bind the stated member directly, or leave out the extra key, to get its encoding.

In a stacked query or header group, such a union bound after a schema that states a field writes
that field as the caller gave it, as `Schema.Struct({})` already did there on 0.18. After
`Schema.Struct({ token: Schema.StringFromBase64 })`, `{ a: "x", token: "hi" }` sends
`?a=x&token=hi`, where 0.18 sent `?token=aGk%3D&a=x`. A field the earlier schema renames goes out
under both names: `?sort_by=n&a=x&sortBy=n`. Bind the union first to keep the other schema's
encoding; [schema groups](../schema-groups.md) gives the rule.

## Give Void nothing to erase

Built-in `Schema.Void` takes only `undefined`, `null`, or an object or list that holds nothing,
anywhere. Anything else goes to another member of its union, or is refused:

<<< ../../examples/migration-0-19.ts#voids

On 0.18 `label` and `said` prepared `null`, and `erased` and `scalar` prepared `{"ack":null}`. On
0.19 the empty struct keeps `label` as `{"tag":"a"}`, `said` prepares `"hello"`, and `erased` and
`scalar` refuse at `["ack"]`; their input is untyped, hence the casts. A `Date` or a `Map` given to
Void refuses too. `empty` prepares `{"ack":null}` on both. A union beside Void in a class's field
keeps its object too, and a one-of union of Void and a struct accepts a populated value of the
struct's own, which 0.18 refused as ambiguous with the struct first and sent as `null` with Void
first.

## Encode values JSON cannot represent

<<< ../../examples/migration-0-19.ts#json

On 0.18 `notANumber` sent `{"v":null}`, `map` sent `{"v":{}}` and `rebuilt` sent `{}`. On 0.19
`notANumber` and `map` fail with `HttpBodyError` naming `["v"]`, and `rebuilt` with `SchemaError`,
because its schema rebuilds the `Map` before the writer sees it. Convert the value, as `written`
does, or use a schema that encodes it. The writer also refuses functions, symbols, BigInt, bytes,
collections, `undefined` in a list and an array's own named fields. Plain objects, class instances
and values with `toJSON`, such as `Option`, write as before.

These checks apply to what reaches the writer unconverted, as under `Body.json` and `Schema.Any`.
`Schema.Unknown` already refused all of these on 0.18, with `Expected JSON value`. Under
`Schema.Number`, Effect's JSON codec writes `NaN` and `Infinity` as the text `"NaN"` and
`"Infinity"`, as on 0.18; use `Schema.Finite` to refuse them.

`Body.text`, `Body.bytes`, `Body.empty`, `Body.formData` and `Body.urlEncoded` refuse what they
cannot write in the same way. Multipart no longer skips a number or `null`, and `Body.urlEncoded` no
longer writes `k=null` for a `null`. **Their error types, and those of every `Body.encodeSchema`
encoder, now include `HttpBodyError`**, so a handler written against `SchemaError` alone has to
handle it.

Encoding a large JSON body takes about three to four times 0.18's time on Node 24, and six to eight
times on Node 26: 10,000 rows take 5.75 ms there instead of 0.9 ms.

## Send scalars in queries and headers

<<< ../../examples/migration-0-19.ts#group-values

On 0.18 `object` sent `?b=[object Object]` and `pair` sent `?k=v`, dropping its third position. On
0.19 both fail with `InvalidRequest`. Encode an object to text first, as `text` does. Query fields
take scalars and flat lists of scalars; a pair is a list of length two with a string name. A list of
pairs is read by its positions, so an iterator on it has no effect, and a one-shot iterator of pairs
is read once. A `Date` is written from its own timestamp whatever realm it comes from.
`Request.setQuery` and `Request.appendQuery` throw `TypeError` for an unsupported fixed value.

## Update

```sh
npm install viell-effect-schema-http@0.19.0
```

Before updating, look for:

- Input that mixes a renamed field's two names, or lists and records whose items are on different
  sides.
- Unions that hold `Schema.Unknown`, `Schema.Struct({})` or `Schema.Void` beside another member, and
  `Schema.Void` fields that can be given a value.
- `Schema.Any` and `Body.json` bodies that can hold `NaN`, a `Map`, bytes or `undefined` in a list,
  and a `Map` or `Date` given where a schema such as `Schema.Record(Schema.String, Schema.Unknown)`
  reads an object.
- Multipart bodies that can hold numbers, booleans or `null`, URL-encoded bodies that can hold
  `null` or dates, and query values that can hold a `Redacted`. These refuse with `HttpBodyError` or
  `InvalidRequest`, where 0.18 left the field out or sent text such as `null` or `<redacted>`.
  URL-encoded numbers and booleans are written as before.
- Objects in query values, and stacked query or header groups with an open union member.
- Handlers on body encoders that expect only `SchemaError`.
- `Body.json` values with getters or `toJSON` methods that can throw: such an exception is now a
  defect, where 0.18 returned `HttpBodyError`.

Add a request test for each. Most such calls now refuse before dispatch, with an error that names
the value; a stacked group sends a different request instead.

## Also in 0.19

- `Body.urlEncoded.pipe(Body.encodeSchema(schema))` type-checks for a schema whose encoded side is a
  record of fields, as [the Body guide](../modules/body.md) shows for a token request. The types
  `UrlEncodedInput`, `UrlEncodedRecord` and `UrlEncodedValue` describe what it takes.
- `Response.UnexpectedResponse` and `Response.DecodeError` have messages that give the status, so an
  uncaught failure no longer prints only its tag. Code that compared either message with the empty
  string needs updating.
- A query or header refusal for an output that is neither a field record nor field pairs says what
  is wrong with it, such as the position of a malformed pair.

## Bounds

[Limits](../schema-input.md#active-limits-and-recovery) lists what preparation cannot see, with the
reason: values that are not plain data, opaque values and custom transformations, names every object
has, and unions that choose again on a transformed copy. It also lists valid input that is refused
because no reading the library may choose keeps it.
